# HOMEONLY3 — Keep Menu3 alive when Home exits

Date: 2026-09-29

## Device evidence from HOMEONLY2

User confirmed HOMEONLY2 restored the correct baseline:
- Menu3 touch/input works again.
- Java/J2ME remains removed.
- Selecting **Vào màn hình chính** shows the real Home Screen briefly.
- Then the visible sequence is:
  1. Home Screen appears;
  2. EKA2L1 returns to its app library;
  3. about 1–2 seconds later the iOS app exits to the iOS Home Screen.

The uploaded persistent log also shows a clean emulator shutdown boundary:
- Central Repository changes are flushed.
- graphics queue reports a clean stop.
- a new emulator session starts immediately afterwards.

The captured log after that reset no longer contains a useful Home-specific final panic window; GetString diagnostics visible in the retained session are from ALF/Menu, not the final Home process.

## Root cause in host lifecycle

The historical iOS frontend implements:

`onAppExited -> exitGame -> bridge::exit_game -> shutdown/restart emulator`

for every launched guest UID.

That policy is correct for ordinary games but conflicts with the M3HOME architecture:
- Menu3 is deliberately kept alive;
- Home UID 0x102750F0 is launched on top of Menu3;
- if Home exits/panics, the callback reboots the entire emulator instead of leaving Menu3 alive.

This explains the observed Home -> EKA library reset chain and destroys the diagnostic window needed to isolate the remaining Home guest failure.

## HOMEONLY3 change

File:
`apply_homeonly3_homeexitkeep1.py`

Only when:
`currentGameUid == 0x102750F0`

HOMEONLY3:
- does NOT call `exitGame()`;
- does NOT call `bridge::exit_game()`;
- does NOT modify guest/kernel behavior;
- restores host bookkeeping to Menu3 UID 0x101F4CD2;
- reloads Menu3 key bindings;
- keeps `gameRunning=YES` and emulator surface alive.

All non-Home guest exits keep the original reboot-on-exit behavior.
